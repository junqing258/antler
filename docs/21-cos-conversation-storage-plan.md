# 腾讯云 COS 会话历史存储方案

> 状态：待实施（单 backend、低并发版本）
>
> 日期：2026-11-04
>
> 目标：将后端容器本地的会话历史文件迁移至腾讯云 COS，保持现有 Web、移动端与 HTTP/SSE 协议兼容，并明确存储故障时的可用性与数据丢失边界。

## 1. 背景与范围

当前 `ConversationStore` 将会话消息和运行事件写入本机 JSONL，将模型上下文 checkpoint 写入本机 JSON。数据库只保留会话元数据、同步游标和 checkpoint 的安全镜像。这使容器重建、跨机器迁移和本地磁盘丢失存在历史丢失风险。

本方案把下列会话有效载荷迁至 COS：

- 用户与助手消息快照；
- Run 事件（用于重放与中断恢复）；
- checkpoint 和 `contextState`。

不在本次范围内：前端直传 COS、技能文件/工作区迁移、跨实例调度与运行租约改造、多个 backend 实例同时写入同一会话。当前仍遵守“一个数据库只运行一个 backend 进程”的部署约束；同一会话的读写仅由现有进程内串行队列协调。

与 [多实例部署与对象存储方案](./15-multi-instance-and-object-storage-plan.md) 的长期目标不同：该文档的阶段性建议是将在线会话迁回 PostgreSQL；本方案则在保持当前文件型会话模型的前提下，将其权威介质从本地卷替换为腾讯云 COS。实施前须明确采纳本方案，或统一修订两份文档的长期架构决策。

本仓库先前已经采用过 PostgreSQL 的 `ConversationMessage` 和 `RunEvent` 作为会话正文/事件存储；2026-10-22 的 commit `d88022a`（“会话消息改用本地 JSONL 存储并实时推送运行事件”）将其迁至本地 JSONL，动机是实时事件推送不等待数据库写入，并非记录在案的性能或成本决策。因此，COS 的选择不能仅凭“对象存储更便宜”成立：实施前必须完成 §8 的一次对比压测并记录结论。本版在用户已选择 COS 的前提下定义实现路径，不宣称它优于 PostgreSQL 的在线事务模型。

## 2. 当前实现和约束

| 责任 | 当前实现 | 迁移后的要求 |
| --- | --- | --- |
| 会话记录 | `apps/backend/src/conversations/local-storage.ts` 的 `messages.jsonl` | 对象存储中的不可变批次和快照 |
| checkpoint | `checkpoint.json` | COS 独立对象；Postgres 继续保留安全镜像 |
| 会话元数据、标题、revision、SSE 游标 | PostgreSQL | 保持不变 |
| 客户端 API | `/api/conversations/*` | 保持不变 |
| 旧数据库记录 | `messageStorage=database` 时按需导入本地 JSONL | 改为按需导入 COS |

接口边界应保留 `create`、`persist`、`messages`、`page`、`events`、`input`、`checkpoint`、`saveCheckpoint`、`importLegacy` 与 `remove`。`ConversationStore` 只依赖这一抽象，不直接依赖文件系统或 COS SDK。

现有流式路径不是逐 token 同步落盘：`RunEventBuffer` 先立即发布普通 SSE 事件，再以 2 秒窗口调用 `appendEvents` 批量持久化；`run.started` 与终态等状态事件才会强制 flush。迁移后必须保持此交互顺序，不能让普通 token 等待 COS 响应。

## 3. 配置和安全

后端从仓库根目录 `.env` 加载配置。当前环境已具有 COS 凭据、地域和桶名；不得将实际凭据写入代码、文档、日志或测试快照。

新增应用级配置：

```dotenv
# local 为默认值；切换后使用 COS。
ANTLER_CONVERSATION_STORAGE=cos

# 仅供本业务使用的对象前缀；不得与技能产物混用。
ANTLER_COS_PREFIX=antler/conversations/v1

# 复用现有 COS 配置。
COS_SECRET_ID=
COS_SECRET_KEY=
COS_TOKEN=              # 可选：临时凭据
COS_REGION=
COS_BUCKET=
COS_SCHEME=https        # 可选，默认 https
COS_ENDPOINT=           # 可选，私有或兼容端点
```

实现要求：

1. 在 `apps/backend/src/config/env.ts` 的 `AppConfig` 中增加存储模式、前缀和 COS 配置；`cos` 模式下缺少 `COS_SECRET_ID`、`COS_SECRET_KEY`、`COS_REGION` 或 `COS_BUCKET` 必须启动失败。
2. `COS_TOKEN` 仅在临时密钥场景传给 SDK；`COS_APP_ID` 可继续供技能环境使用，但会话存储只使用已带 APPID 后缀的 `COS_BUCKET`。
3. 通过既有受保护环境变量与日志脱敏机制，保证错误日志只输出对象键摘要、HTTP 状态和 COS request ID，不输出授权头、SecretId、SecretKey、Token 或对象内容。
4. 使用最小权限 CAM 子账号：限定此前缀下的 `cos:GetObject`、`cos:PutObject`、`cos:DeleteObject`；迁移/清理任务如需列举对象，再增加受限的 `cos:ListBucket`。

腾讯云 Node.js SDK 支持对象读、写、删除；权限要求以腾讯云的[对象操作文档](https://cloud.tencent.com/document/product/436/64958)为准。

## 4. 存储模型

### 4.1 对象键

对 `JSON.stringify([userId, conversationId])` 求 SHA-256，得到 `conversationKey`。不把原始用户 ID、会话 ID 或标题放入对象键。

```text
${ANTLER_COS_PREFIX}/${conversationKey}/
  manifest.json
  snapshots/<generation>.json
  batches/<generation>/<batch-id>.json
  checkpoints/<checkpoint-id>.json
```

- `batch-id` 使用 UUID/ULID，不复用文件名，也不基于用户输入构造。
- `checkpoint-id` 使用 ULID；会话 `revision` 不参与 checkpoint 对象命名，因为保存 checkpoint 不会递增该 revision。
- `generation` 是紧凑快照世代号。
- 删除采用数据库墓碑优先；正常删除仅依据 manifest 列举的可达对象，不要求应用运行身份拥有 `ListBucket`。

### 4.2 内容格式

`batches/*` 沿用当前 `Batch` 语义：

```ts
type Batch = {
  version: 1;
  messages: LocalMessage[];
  events: RunEvent[];
};
```

`snapshots/*` 保存截至指定批次的消息状态、全部可重放事件和对应水位；`manifest.json` 保存当前版本、有效 snapshot、后续 batch 的完整对象键与水位、当前 checkpoint 对象键、格式版本和提交序号。每个对象写入 `application/json; charset=utf-8`；内容哈希记录在 JSON 体内的固定字段（如顶层 `sha256`，覆盖除该字段外的载荷），不依赖 COS 自定义元数据（其有总量限制且需 `x-cos-meta-*` 前缀）。

读取顺序是：读取 manifest → 读取 snapshot → 按确定顺序重放其后的 batches。未被当前 manifest 引用的对象不对新读取可见，但可能是正在提交的对象或旧读取仍在使用的对象；只有满足 §4.4 清扫条件后才能删除。

### 4.3 写入与紧凑

不能用“每次输出都 PUT 一份完整会话 JSON”替代 JSONL：流式 token 会导致高频全量上传，也会在失败重试时扩大覆盖风险。单 backend 版本复用已有的 2 秒事件窗口；一个窗口内的全部普通事件构成一个 COS batch。

普通 token 的 SSE 推送不等待该 batch 写入。存储适配器为每个会话缓存已加载的 manifest 和消息投影，且由 `ConversationStore` 的进程内队列串行调用；因此常规 batch 不需要“每次 PUT 后再 GET manifest”。服务启动或缓存失效时才读取一次 manifest。

可靠性边界：普通 SSE 是即时展示而非持久化确认。进程异常退出可能丢失尚未形成并写入暂存的 2 秒窗口内事件，也可能丢失该窗口内已发出的 SSE；设备故障或本地卷丢失还可能丢失全部尚未提交 COS 的暂存。重连以已提交的 COS 历史为准，不承诺已展示的普通 delta 均可重放。暂存必须位于跨容器重建保留的持久卷，启动时验证可写和剩余容量；如需覆盖卷损坏或零数据丢失，须另行引入独立持久日志，本方案不提供该保证。

正常收尾时先结束流并 flush 本 run 的全部普通事件，确认消息投影及正文水位已提交，再导出 checkpoint。checkpoint 对象记录所属 run ID 和该正文水位；终态提交引用这个 checkpoint，并在同一版 manifest 中公布终态事件、最终消息投影和 checkpoint 指针。没有可恢复上下文时，终态提交明确记录 `contextState=unavailable` 并清除旧 checkpoint 指针，不能把上一轮 checkpoint 当成本轮结果。完成上述提交和数据库更新后才发布终态 SSE、允许下一次 run。实现须调整现有 `finish` 中独立保存 checkpoint 的顺序，使 checkpoint 不会先于本轮已输出内容可见。

创建会话或启动 run 也属于持久化操作，必须在同一会话队列中执行以下协议，不能沿用数据库写入空 `input` 后再尽力写文件的顺序：

1. 生成稳定的创建提交 ID 和 run ID，将完整用户输入、初始消息投影、请求去重信息及恢复所需 run 数据原子写入持久暂存并完成持久化；失败则拒绝请求，不创建 run 或启动模型。暂存包含敏感正文，遵守暂存卷的权限和删除策略。
2. 先以创建提交 ID 在 Postgres 事务中校验所有权、`expectedRevision`、活跃 run 和请求去重，并幂等创建待完成的会话（如需要）、run、`activeRunId` 及创建记录；数据库不保存正文。随后以稳定 ID 幂等提交初始 COS 对象和 manifest，最后幂等完成数据库正文水位、revision 和变更事件。待完成状态必须阻止读取为完整会话及启动其他 run。只有两侧均确认后才能接受请求并启动模型；结果不确定时查询提交记录和 manifest 对账，不重复创建或启动。
3. 创建意图在确认数据库事务后才删除。启动恢复先处理创建意图：若数据库尚无创建记录，重新执行事务校验；确定发生业务冲突时放弃意图并清扫其对象。数据库已预留时补齐 COS 和最终事务，并确认初始输入可读，然后才允许中断恢复。无法确认时阻塞该会话并重试，不将缺失输入当作空输入。客户端重试使用原请求去重语义返回同一 run；崩溃后不自动重新执行模型，而按中断恢复规则处理。

写入流程：

1. 每个 2 秒窗口或达到 1,000 条时封装 batch，先将带稳定 batch ID、顺序号、内容哈希和重放所需 run 投影的记录原子写入持久暂存并完成持久化，再上传 COS。普通 SSE 不等待暂存或 COS；暂存成功之后才将该 batch 视为可恢复。目录和文件权限沿用本地存储的限制。上传超时按相同 ID 和内容重试。checkpoint 使用新的 ULID 对象键。
2. 基于会话串行队列内的当前 manifest 上传下一版；每次提交带唯一提交 ID 和单调序号。manifest PUT 超时属于结果不确定：停止该会话后续提交并重新读取 manifest，若包含相同提交 ID 则视为成功；若仍为前一版则以相同内容重试；任何其他版本或无法确认时保持阻塞并告警。确认成功后才更新缓存、删除暂存；暂存删除前崩溃时以提交 ID 幂等识别，不能重复应用事件。单 backend 模式不支持其他写者。
3. manifest 是会话正文、事件与 checkpoint 指针的权威；数据库 `storageGeneration` 仅为诊断 hint。每次正文提交后的数据库正文水位、revision 和变更事件更新必须幂等，并由持久提交记录跟踪，恢复时先对账；不可因 hint 落后回退历史。checkpoint 镜像失败须告警并重试，不覆盖较新的镜像。
4. 同会话严格按序提交；前序未确认时后续批次只入暂存，不提交 manifest。暂存按字节和记录数设置有界容量并监控，达到高水位时暂停新 run 和生产事件；无法暂停或暂存写入失败时中止运行并保留已持久数据，明确报告存储故障，禁止静默丢弃并宣称完整。容量、磁盘预留和告警阈值上线前确定。
5. 终态先把真实终态、终态事件、消息投影及稳定提交 ID 写入持久暂存，然后依次确认 COS manifest 提交、幂等提交 Postgres run 状态/`revision`/`activeRunId` 和变更事件，最后发布终态 SSE。Postgres 事务以 run ID 和提交 ID 去重；事务响应丢失时查询提交记录确认，不能重复递增 revision。终态意图在数据库事务确认后才删除。
6. 启动时在接受请求和执行 `recoverInterrupted` 前，按会话顺序重放暂存并对账终态意图。若 COS 已含终态但数据库仍为运行中，按持久意图补齐数据库事务，绝不能再生成 `interrupted`；只有确认没有终态意图或已提交终态的运行才标记中断。读取 COS 或持久卷失败导致无法判断时保持该会话不可写并重试，不猜测终态。重启后无在线 SSE 监听者时，客户端通过历史事件和变更游标恢复。
7. COS 持续不可用时，真实终态保持待提交，数据库保留非终态且 `activeRunId` 不清空；不发布终态事件、不允许同会话启动新 run。终态等待超时只触发监控和可重试的服务不可用响应，不将 run 伪装为 `failed` 后再改回成功。恢复后按第 5 条提交唯一真实终态。现有客户端对长时间运行和断线重连的表现须验证；若需要展示“历史保存中”，须单独设计兼容的状态接口，不能冒充终态。
8. 删除采用 §4.5 的数据库持久任务，和该会话所有提交、恢复操作串行；墓碑建立后禁止新提交及暂存重放复活会话。checkpoint 镜像和本地暂存也纳入删除范围。
9. 终态 flush 后及自上次 snapshot 累计 batch 达到阈值时生成 snapshot，保留全部可重放事件和消息投影，再提交新 manifest。旧对象按 §4.4 延迟清扫。snapshot 保留全部事件，长会话仍会导致 snapshot 体积和紧凑成本增长，上线前须压测并设定大小上限及超限处理。

### 4.4 垃圾回收

GC 使用独立身份运行，应用身份不需要 `ListBucket`。GC 只处理不可变 snapshot、batch 和 checkpoint，不按年龄直接删除 manifest 或可能仍可达的对象。扫描先记录候选及首次发现时间；至少经过配置的宽限期后，逐会话进入与写入、紧凑和删除相同的串行协调域，重新读取 manifest 和持久暂存/迁移任务引用，确认对象仍不可达且不属于在途提交后才删除。宽限期必须大于允许的最长读取、提交和迁移时长；读取设置有限超时，旧读取结束前不得清扫其引用对象。GC 必须由单 backend 调度或在停写维护窗口执行，不能独立于进程内协调并发运行；无法确认引用或协调失败时跳过。清扫幂等并记录进度。禁止对包含有效对象的前缀配置按年龄过期规则；生命周期只能用于经过隔离且确认不含可达或在途对象的前缀。启用版本控制时须明确非当前版本、删除标记及副本的保留和物理删除策略，未验证前不得宣称物理删除完成。

### 4.5 删除恢复

在同一个 Postgres 事务中写会话墓碑、变更事件和唯一持久删除任务；任务包含会话身份、阶段和可恢复的对象键清单。工作器先读取 manifest，将所有已知可达键持久记录到任务，再删除数据对象，确认完成后最后删除 manifest；每一步均可重试，404 视为已删除。若读取 manifest 失败，任务保持待重试，不能把失败当空会话。工作器同时清除本地暂存和数据库 checkpoint 镜像；墓碑阻止后续写入。历史孤儿由 §4.4 清扫，版本及备份按保留策略处理；任务状态区分在线对象删除完成与所有副本物理删除完成。崩溃后从任务阶段续跑，不依赖内存队列。

`storageGeneration` 可记录在数据库中用于诊断、迁移进度和垃圾清理，但单 backend 版本不引入数据库条件更新协议，也不把消息正文、事件 payload 或 checkpoint 正文写入该字段。开发与线上环境不得共用同一数据库并同时启动 backend；若该部署约束不再成立，必须先实施多写者方案，不能依赖本版进程内队列。

此方案不依赖 COS `APPEND Object`。追加对象要求 appendable 类型，并受 5GB、存储桶多 AZ、版本管理和生命周期限制，不适合作为会话可靠性基础；详见腾讯云 [APPEND Object 文档](https://cloud.tencent.com/document/product/436/7741)。

## 5. 后端改造

1. 新增 `ConversationStorage` 接口，将 `LocalConversationStorage` 改为该接口的本地实现。
2. 新增 `CosConversationStorage` 和窄封装的 COS client；SDK 调用统一转换为 Promise、设置连接/请求超时与指数退避重试，并按操作上下文分类 404：仅在明确允许不存在的创建探测及幂等删除中视为不存在；已标记 `cos-v1` 的会话缺少 manifest，或 manifest 引用的 snapshot、batch、checkpoint 缺失，均报告存储完整性错误并告警，禁止返回空历史或静默降级。
3. 注入存储路由器，同时持有 local 和 COS 实现；`ANTLER_CONVERSATION_STORAGE` 只决定新会话的目标介质，不覆盖已有会话的 `messageStorage`。`database` 从旧数据库读取或导入目标介质；`local-jsonl` 继续从本地读写并可重试迁移；`cos-v1` 始终读写 COS。COS 模式下仍须挂载旧卷直到全部迁移及回滚窗口结束。已有 `cos-v1` 的环境即使默认模式为 local，也必须配置 COS；缺失时启动失败或明确拒绝该会话，不能返回空历史。
4. `ensureStored` 在会话队列内按标记选择来源；导入后从目标重新读取并校验，成功才原子更新标记。标记更新结果不确定时重新查询；失败保留旧来源，迁移与写入互斥。显式迁移脚本与运行服务不得同时操作同一会话。
5. 改造 `RunEventBuffer` 与运行收尾，执行 §4.3 的有界暂存、背压、终态意图和恢复协议；保留普通 SSE 即时发布及其明确的丢失窗口。
6. 增加有界 LRU 缓存，以独立于会话 `revision` 的正文提交水位标识不可变投影；数据库持久记录已对账的正文提交 ID/序号，manifest 保存对应序号。创建、正文 batch 和终态提交推进正文水位；重命名等纯元数据更新只推进会话 revision 和变更游标，不要求产生正文提交。读取在会话队列内取得数据库元数据与正文水位，并确认 manifest/缓存投影与该水位一致；manifest 已提交但数据库尚未对账时先完成对账，无法确认则报错或等待重试。返回的 revision 是同次读取的元数据 revision，不以其数值判断正文水位。删除后先验证墓碑再返回缓存。详情、分页、事件补放均遵守此规则；缓存失效或校验失败时重新加载。无锁读取仅在能够原子验证墓碑、元数据版本及正文水位时允许，否则进入队列。
   会话队列只串行化单次有界操作；连续批次分别入队，不能由单个任务持续占用队列处理整个流。读取请求在批次之间公平执行，并设置有界排队容量和等待时间，超过限制时返回明确的可重试错误。紧凑的快照构建尽量在队列外基于已固定的不可变水位进行，提交 manifest 前重新进入队列并验证水位；水位变化时重新生成或放弃本次紧凑。
7. 实现 §4.4 的协调式 GC 和 §4.5 的持久删除任务。数据库新增 `storageGeneration` 诊断字段、已对账正文水位、提交去重/恢复记录和删除任务所需字段或表，随变更提交 Prisma 迁移；明确这些记录的保留、清理与权限。

## 6. 迁移与上线

### 6.1 迁移工具

新增受显式命令触发的迁移脚本，不在服务启动时批量扫描：

1. 枚举数据库中 `messageStorage=local-jsonl` 的未删除会话；
2. 从旧目录读取 JSONL 与 checkpoint，按现有容错规则忽略截断尾行；checkpoint 选择遵循现有运行时：本地 checkpoint 存在且可解析时使用本地 `checkpoint` 和 `contextState`；本地缺失时使用数据库 checkpoint 安全镜像及其 `contextState`，两者均无 checkpoint 时按现有逻辑标记 `not_restored`。本地文件存在但损坏或无法读取时记录失败并保留旧标记，不把错误当作缺失；比较并记录来源及哈希，不将正文写入报告。数据库镜像是安全副本，不能假定与丢失的本地原件完全相同；
3. 写入 COS 新世代；
4. 比较消息数、序号、事件数、最后事件 ID、消息投影哈希和 checkpoint 哈希；
5. 仅在全部校验通过后更新为 `cos-v1`；输出成功、跳过与失败清单，支持安全重跑。

数据库旧存储（`messageStorage=database`）继续通过 `ensureStored` 按需迁移；也可由迁移工具统一处理。

### 6.2 部署顺序

1. 备份 Postgres 与现有会话本地卷，确认可恢复。
2. 部署包含 `local` 和 `cos` 双实现的版本（含 `storageGeneration` 字段的 Prisma 迁移），先保持 `ANTLER_CONVERSATION_STORAGE=local`。
3. 配置最小权限 CAM、COS 生命周期/加密策略和应用环境变量；执行只读连通性检查。单独配置长期持久暂存卷及路径，确保跨容器重建保留、仅服务身份可读写；验证原子写入与持久化语义、启动可写检查、容量预留、高水位告警和重启重放。确定备份及卷损坏后的处置和数据丢失边界。暂存卷可与旧卷物理共用，但须独立管理目录和生命周期。
4. 停止会话写入或进入维护窗口，执行迁移与完整校验。
5. 确认迁移报告无未解决失败项后切换 `ANTLER_CONVERSATION_STORAGE=cos`，启动单实例后端；未迁移会话仍由路由器使用旧来源，不能把它们当作空 COS 历史。若允许带失败项上线，必须事先确认旧卷可用并明确逐项重试责任。
6. 抽样验证历史浏览、分页、继续对话、服务重启恢复、取消和删除。
7. 旧历史本地卷至少保留一个确认周期；确认备份与回读演练通过后，再按保留策略清理旧历史。长期暂存目录和挂载不得随旧历史清理，须持续监控容量并定期演练恢复。

### 6.3 回滚

- 暂停写入并完成或安全停止在途提交后再回滚；默认模式切换不会改变既有 `cos-v1` 的读取路由，也不能单独完成回滚。
- 即使 COS 切换后没有新写入，也须核对每条已迁移会话的本地源与 COS 校验值，在维护窗口内将验证通过的标记恢复为 `local-jsonl`；数据库旧来源按原标记恢复。仅当所有目标标记和数据验证完成后，才能启动不支持 COS 的旧版本。
- 已有新 COS 写入时，通过本次交付的反向导出工具将每个 `cos-v1` 会话写入独立临时本地目录，校验消息、事件、checkpoint 和水位后原子替换目标并更新标记；记录每会话进度，操作可重跑。任何失败项保留 COS 标记并阻止回退旧版本；保留 COS 数据直至回滚验证完成。
- 单个会话迁移失败保持原 `messageStorage`，由路由器继续访问原来源并重试；原来源不可用时返回明确错误，不得返回空历史。

## 7. 测试和验收

新增单元与集成测试至少覆盖：

- COS 配置校验、凭据脱敏和 SDK 错误归类；创建探测与删除允许的 404，以及已提交 manifest 或其引用对象缺失时的完整性错误；
- 新会话及已有会话创建 run，在创建意图落盘、COS 提交、数据库事务及响应丢失等阶段注入崩溃；验证输入可恢复、请求重试不重复创建或执行、业务冲突不复活会话；
- 创建、流式批次持久化、重复提交幂等、消息分页、事件增量读取和 checkpoint 覆盖；
- 正常收尾时验证普通事件和消息投影先于 checkpoint 提交，终态与对应 checkpoint 水位一致；无可恢复上下文时不复用旧 checkpoint，终态发布前不得启动下一 run；
- 上传失败、上传成功但 manifest 更新失败、读取超时、终态强制 flush 和删除失败重试；
- 前序 batch 提交失败时同会话后续 batch 阻塞提交且事件不乱序；暂存重放按序完成；
- 注入窗口内、暂存前后及卷丢失故障，验证明确的数据丢失边界；持久暂存的批次在重启后有序恢复，恢复先于中断运行标记；
- 积压达到 1,000 条触发 flush；暂存高水位、写入失败和容量耗尽时验证背压、中止及告警，不静默丢弃；
- 紧凑触发（终态 flush 与 batch 数阈值）后 manifest 仅引用新 snapshot 及其后 batch，孤儿对象可被 GC 识别；
- 普通 SSE 不等待 COS；2 秒合并窗口内多个 delta 只形成一个 batch；COS 暂时失败后重试成功时不丢消息、不重复事件；
- 同一会话在未递增 `revision` 的情况下连续保存 checkpoint，验证生成不同 ULID 对象并且 manifest 始终指向最新 checkpoint；
- 分别在 batch 上传、manifest 写入、数据库 hint 更新和 checkpoint 镜像更新后注入崩溃，验证以 manifest 恢复、修复 hint 且不会回退历史；
- 墓碑事务及删除各阶段崩溃后任务可续跑；验证旧版本、备份及本地暂存的删除状态；GC 与在途上传、慢读取、紧凑、迁移交错时不删除可达或在途对象；
- LRU 容量淘汰、TTL 到期、写入刷新、删除失效及并发读取的一致性；验证重命名等仅推进 revision 的操作不会阻塞读取，正文水位未对账时不返回不一致投影；
- 连续流式批次和紧凑期间，同会话分页读取能够在批次之间完成；排队达到容量或等待时间上限时返回可重试错误；
- 紧凑前后消息投影与所有事件一致；
- 本地 JSONL（包括截断尾行）迁移后，消息、事件、终态和 checkpoint 一致；覆盖仅数据库镜像存在、两者均不存在以及本地 checkpoint 损坏的情况；
- `ConversationStore` 对 `database`、`local-jsonl`、`cos-v1` 三种状态的兼容迁移；
- manifest PUT 和数据库事务响应丢失、COS 终态提交后数据库更新前崩溃，验证幂等对账、唯一终态、revision 不重复及不误标 interrupted；COS 长期不可用时验证客户端断线重连及恢复行为；
- 部分迁移、切换模式、无新写入和有新写入的回滚及中途崩溃重跑；
- 现有 Web 与移动端会话 API 回归测试。

上线验收标准：

- COS 中任意已迁移会话可在服务重启后完整加载；
- 不出现“存储异常被当作空历史”的响应；暂存持久卷的重建保留、容量告警和重放演练通过；
- 迁移报告所有目标会话均完成数量与哈希校验，或明确列入失败清单；
- 密钥、令牌、原始会话内容不出现在应用日志、测试输出或指标标签；
- 实际部署主机到目标 COS 的压测报告已记录：普通 SSE 不等待 COS 或暂存；2 秒窗口内 COS batch 的 P50/P95/P99、失败率、连续失败恢复时间、终态强制 flush 时延，以及流式进行中的同会话分页读取 P95 均满足本次确定的上线阈值；
- `pnpm check` 与 `pnpm test` 均通过。
