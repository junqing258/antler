# Mobile 应用配置与界面对齐方案

## 背景与目标

当前 Mobile 仍以验证流程为主：用户需要进入配置界面填写服务端地址、认证信息和会话 ID，供应商配置也与 Web 的字段和交互不完全一致。本方案将 Mobile 调整为面向用户的应用流程。

目标：

- 应用自动读取后端地址，用户无需填写连接参数即可开始使用。
- 首页、聊天、登录及设置的界面逻辑与 Web 保持一致，并适配移动端交互。
- 供应商配置的字段、保存规则、模型选择及会话绑定行为与 Web 一致。
- 保留现有设备上的供应商配置，避免升级造成凭据或模型丢失。

本方案中的“免配置页”指移除服务地址、认证模式、访问令牌和会话 ID 等技术参数的手工配置页。供应商设置仍作为用户可访问的设置功能保留。

## 当前实现

- `mobile/src/app.tsx` 使用状态切换首页与聊天验证界面，并暴露流式诊断入口。
- `mobile/src/native-config.ts` 默认服务端地址为空，供应商模型列表保存为逗号分隔的字符串。
- `mobile/src/native-storage.native.ts` 使用 AsyncStorage 保存普通配置，使用 SecureStore 保存访问令牌和供应商 API Key，且凭据与对应地址等信息绑定。
- Web 的供应商配置包含名称、协议、Base URL、API Key、模型列表和当前模型；`packages/ui/src/provider-config-form.tsx` 已提供跨端共享表单。
- Mobile 已复用共享聊天组件和客户端运行时，可在现有基础上调整，不需要重建聊天协议。

## 方案

### 1. 后端地址与启动

本期正式发布目标是具备可信 HTTPS、且采用 Supabase 或无需访问令牌的 local 认证的部署；受令牌保护的 local 部署仅支持下述旧设备场景。当前生产部署的 HTTPS 和认证状态尚未确认，须在实施及发布前核实；若现有部署只有 HTTP，应先提供 HTTPS 入口或重新确定发布方案，不能视为已满足目标。

通过 Expo 应用配置注入后端地址，按开发、测试、生产环境提供对应值。增加统一的配置读取和校验入口，供首页、认证、普通 API 和流式请求使用，避免不同请求使用不同地址。

- 正式构建要求 HTTPS；开发环境允许 HTTP。iOS 当前 ATS 配置不允许本地网络访问，开发或专用测试构建须按目标主机配置必要的 ATS 例外，并验证真机可达；正式构建不包含这些例外。Android 同样按构建类型配置明文流量策略。
- 配置缺失或格式错误时展示可理解的启动错误；网络不可达时提供重试，不要求用户手动填写地址。
- 应用配置只包含公开地址，不打包服务端令牌、供应商 API Key 等秘密。
- 构建时注入的地址是权威来源，旧设备保存的地址不覆盖它。地址变化时，不将绑定到旧地址的 local 模式访问令牌发送给新地址。
- 本期全新安装支持 Supabase 登录和不要求访问令牌的 local 部署；要求 `ANTLER_ACCESS_TOKEN` 的 local 部署不支持全新安装或重新配置凭据。升级设备仅可继续使用与当前后端地址及 local 模式匹配的旧令牌，后端拒绝该令牌时提示联系部署管理员改用受支持的认证方式。不得为了使应用可用而要求管理员关闭公网访问控制；受令牌保护的 local 部署及其新设备接入机制需另行设计。
- 扩展公开的 `/api/auth-config` local 响应，明确返回是否要求访问令牌，不返回令牌本身。客户端在要求令牌但没有匹配旧令牌时展示不支持的部署提示，建议联系管理员使用 Supabase 或部署受信任的访问控制；配置或令牌变更后可重试。新客户端遇到缺少该字段的旧服务端时提示服务端升级，不能假定无需令牌。
- 认证模式及公开认证参数沿用服务端配置能力；需要登录时展示登录流程，令牌刷新与退出登录沿用现有认证实现。仅当接口成功且明确返回有效的 local 配置时进入 local 模式；网络错误、非成功响应或无效配置均进入错误状态并提供重试，不能静默降级。现有 `loadAuthBackendConfig` 的降级行为需要调整。
- 服务端启动时校验 Supabase 所需 URL 和 publishable key；配置不完整或无效时启动失败并给出不含秘密的诊断信息，认证钩子也不得回退到 local。`/api/auth-config` 只有实际配置为 local 时才能返回 local；同步调整服务端和 Web 对该接口的处理及测试，避免接口契约变更造成回归。
- Supabase 会话按规范化认证项目 URL 隔离存储；重新创建客户端时关闭旧客户端的自动刷新和订阅，退出登录仅清除当前项目的会话。只有先成功获取并验证新后端返回的项目配置，才可读取该项目的会话；项目变化时不得向新项目或后端发送旧项目令牌，需重新登录。publishable key 变化时重新创建客户端，但同一项目的会话可继续使用。

默认每个构建环境对应一个后端地址，应用内不提供地址切换。发布前使用与正式包相同的构建配置和注入值，在 iOS、Android 验证实际地址、TLS、认证配置及端到端连通性；自动化不得通过 `autostart` 参数覆盖待验证地址。正式包自身还须进行冒烟验证。地址错误默认通过重新构建发布修复；Expo Updates 是否适用于配置热修需单独评估更新机制、原生配置及回滚限制，本期不依赖它。如果后续需要一个安装包连接多个客户的后端，需要单独设计地址下发和信任机制。

### 2. 供应商配置

在 Mobile 的设置入口中复用 `ProviderConfigForm`，提供与 Web 一致的名称、协议、Base URL、API Key、模型列表和默认模型，以及相同的输入归一化、增删模型、保存和重置行为。设置入口应从首页和聊天中按 Web 对应流程可达。

供应商配置采用与 Web 相同的语义和字段结构，通过平台存储适配：普通字段存入 AsyncStorage，API Key 存入 SecureStore。配置仅保存在当前设备，账号不自动同步 API Key。界面明确告知用户这一行为。

聊天使用与 Web 一致的模型选择和会话绑定规则：

- 配置了本地 API Key 时，使用本地供应商配置和模型列表；未配置时使用服务端默认模型。
- 新会话无本地 Key 时，沿用 Web 请求 `/api/config/provider` 获取默认模型用于展示，获取失败时显示“服务端默认模型”占位且仍可发送；发送不携带 provider，由服务端决定实际配置。已有绑定优先使用会话详情的 `executionConfig` 展示模型、协议及地址。本期不新增模型发现接口。
- 已绑定的会话展示绑定的协议、服务地址及模型；凭据不匹配时引导用户填写匹配配置。
- 切换模型涉及已绑定会话时，按 Web 当前行为处理新会话，避免改变已有会话的绑定。
- 保存设置后，首页和聊天读取最新配置，避免继续使用旧的内存快照；不能因配置变更意外丢失正在输入的内容或中断运行。

优先提取和复用跨端的配置类型、归一化、模型选择逻辑及配置订阅接口；Web 与 Mobile 各自实现符合平台要求的存储和通知适配。Mobile 在成功保存后通过应用内发布订阅通知消费者更新，不能依赖 AsyncStorage 自动产生变更事件。

### 3. 导航与界面

- 启动后读取配置和登录状态，进入首页或必要的登录流程。
- 首页支持直接开始对话、选择 Agent 和打开设置；对话与返回导航遵循 Web 的业务逻辑，并适配移动端屏幕和键盘。
- 会话 ID 由应用生成或根据服务端会话流程管理，不向用户暴露手工输入。
- 移除正式界面中的连接参数表单和流式诊断入口；流式诊断和现有 `autostart` 深链自动化钩子保留在开发或专用测试构建中，正式发布构建必须禁用；验证脚本应适配新启动流程，保持自动连接、发送及取消测试能力。
- 连接失败、登录失效、凭据不匹配、加载中和空状态提供明确提示及可执行的恢复操作。

### 4. 旧配置迁移

首次加载新版本时，读取旧版 Mobile 配置并转换为新的供应商结构：解析和去重旧模型列表，保留已选模型、协议、Base URL 和 API Key；缺失名称使用“自定义供应商”，与 Web 表单提交时的空名称归一化规则一致。迁移时维持已有的凭据绑定检查，只有旧凭据记录的协议和 `providerBaseUrl` 与旧普通配置匹配时才迁移 Key；迁移后该 Key 仍绑定同一协议和 Base URL。

迁移应可重复执行，只有新配置成功保存并可读取后才标记完成；失败时保留旧数据并提示重试。后端地址采用新应用配置，旧地址仅用于判断旧 local 访问令牌是否仍可使用，不作为新地址的覆盖值。旧 `authMode` 不作为新流程的认证模式，仅读取用于旧令牌绑定校验；新模式由服务端决定。旧 `conversationId` 和 `agentId` 不迁移为启动时的当前选择：新启动流程创建或选择会话，服务端历史不删除，并通过正常的历史入口访问（如果该入口尚未完成，应在实施时补齐）。

旧版 Supabase 使用固定存储键，未记录可信的项目身份；不能仅凭新后端返回的配置认定旧会话属于该项目。本期不自动复用该旧会话，要求重新登录，并在新会话成功保存后清理旧存储键。新版本按项目隔离会话；迁移或清理失败时不得将旧令牌发送给新项目，重试不得覆盖已经建立的新会话。

## 实施步骤

1. 确定各构建环境的后端地址注入方式；完成服务端认证配置校验及接口契约更新，增加客户端统一读取、校验和错误状态，让所有请求共享该配置。
2. 整理共享供应商配置类型、归一化和模型选择规则，接入 Mobile 存储适配并实现旧数据迁移。
3. 在 Mobile 接入共享供应商表单与设置导航，串联聊天中的模型选择和凭据恢复流程。
4. 调整启动、登录、首页和聊天导航，移除正式界面的验证配置和诊断入口。
5. 补充自动化测试，完成 iOS 和 Android 的实际使用验证，并更新构建配置说明。

## 验收标准

- 全新安装后，在后端地址已随构建配置注入、后端为 Supabase 或无需令牌的 local 部署且服务可用的情况下，用户无需填写连接参数即可进入首页或登录流程，并开始对话。受令牌保护的 local 部署在无匹配旧令牌时显示明确的部署不支持提示；旧服务端未声明令牌要求时提示升级。
- 首页、登录、聊天及流式请求均连接同一个配置地址；地址缺失、无效或服务不可达时展示相应错误，网络恢复后可重试；认证配置请求失败或返回无效数据不会被当作 local 模式。
- 供应商表单的字段、模型增删、保存、重置和模型选择行为与 Web 一致；重启应用后配置仍可使用。
- 已绑定会话的凭据提示、恢复与模型切换行为与 Web 一致；无本地 API Key 时使用服务端默认模型。
- 旧版有效供应商配置和 Key 可迁移；匹配当前地址的旧 local 令牌可用于升级设备，旧地址对应的令牌不会发送给新的后端。旧版固定键的 Supabase 会话要求重新登录；新版本同项目会话可恢复，不同项目隔离并要求重新登录，退出及项目切换不影响其他项目的会话。
- Supabase 配置缺失或无效时服务端拒绝启动，不能返回 local 配置或回退 local 授权；自动化测试覆盖缺失 URL、缺失 key、旧接口响应、local 令牌要求、项目切换和旧会话迁移失败。
- 正式构建不显示技术配置和流式诊断入口、禁用自动化深链钩子，且不包含服务端令牌或供应商密钥；开发或专用测试构建仍可通过深链执行自动化验证。
- 发版前验证正式构建实际注入的地址可达、TLS 和认证配置正确，并完成 iOS、Android 正式包冒烟测试；测试过程中不得覆盖该地址。
- 自动化测试覆盖配置读取、迁移重复执行及中断后重试、保存、模型选择、凭据绑定和失败状态；运行项目类型检查及相关测试，并在 iOS、Android 验证登录、流式聊天、重启恢复和异常恢复。
