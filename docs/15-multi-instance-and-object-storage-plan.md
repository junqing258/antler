# 多实例部署与 S3 对象存储方案

状态：规划，尚未实施。

日期：2026-10-29。

## 1. 目标与结论

支持多个后端实例服务同一套用户、会话和文件数据，逐步实现 API 横向扩容、执行节点扩容和滚动发布。用户请求落到任意 API 实例时，都能查看会话、订阅运行、取消任务和下载文件。

当前不能直接通过增加后端容器副本实现上述目标。需要先解决本地会话存储、进程内执行状态、启动恢复、定时调度和文件归属问题。

采用 PostgreSQL + S3 兼容对象存储 + Worker 本地磁盘的分层方案。Redis 用于通知加速，不作为任务状态和文件元数据的唯一权威来源。第一阶段以 PostgreSQL 实现任务队列和租约，避免同时引入第二套任务状态机制。

独立部署多套 Antler、各自使用独立数据库和目录，不属于本方案；该方式不提供共享数据和故障接管。

## 2. 当前实现与限制

以下以当前代码为准，历史方案中的描述可能早于本地 JSONL 存储改造。

| 部分 | 当前依据 | 限制 |
| --- | --- | --- |
| 会话存储 | `backend/src/conversations/store.ts`、`local-storage.ts` | 消息、事件与 checkpoint 使用本地文件，串行队列在进程内；共享目录不能替代跨进程并发控制 |
| Agent 执行 | `backend/src/agent/host-runtime.ts`、`pi-agent-adapter.ts` | 活跃 Run、取消控制器、监听器和 Agent 缓存在进程内 |
| 运行恢复 | `backend/src/runs/run-store.ts` | 当前恢复建立在单后端假设上，新实例可能处理其他实例仍活跃的运行 |
| 定时调度 | `backend/src/scheduler/scheduler.ts` | 启动时清理 running 执行并加载任务；周期任务没有集群级触发去重，配置更新只直接作用于本进程 |
| 事件缓冲 | `backend/src/runs/event-buffer.ts` | 缓冲有上限，持久化失败允许丢弃，不满足可靠回放要求 |
| 部署 | `scripts/docker-compose.remote.yml` | 固定容器名、宿主机端口，挂载本地 workspace / platform |
| Redis | `docs/redis.md` | 已有连接配置，应用尚未接入客户端 |

现有 PostgreSQL 元数据、技能文件存储、请求幂等键、会话事务与忙碌检查可以复用。数据库检查仍须结合执行租约和恢复规则完成集群级保障。

## 3. 目标架构

```text
客户端 → 负载均衡 → API A / API B
                         │
                         ├── PostgreSQL：会话、任务、租约、事件、文件元数据
                         ├── S3：附件、执行产物、工作区文件版本
                         └── Redis：事件与取消通知

Scheduler → PostgreSQL 待执行任务 ← Worker A / Worker B
                                       │
                                       └── 本地隔离工作目录 ↔ S3
```

API 负责鉴权、创建运行、查询、SSE 和文件访问授权；Worker 负责执行 Agent 与工具；Scheduler 负责将到期计划转成待执行任务。各角色可使用同一代码库，通过角色配置分别启动。

首期部署两个 API、一个 Worker、一个 Scheduler。此阶段解决 API 扩容与跨实例访问，Worker 和 Scheduler 尚不具备完整高可用；后续通过多 Worker 和 Scheduler 租约补齐。

## 4. 数据与文件存储边界

| 数据 | 权威存储 | 处理方式 |
| --- | --- | --- |
| 会话消息、Run 状态、持久事件、checkpoint | PostgreSQL | 事务提交，支持分页、增量查询与恢复 |
| 用户附件、图片、文档 | S3 | 数据库保存文件元数据与归属 |
| 报告、图片、压缩包等执行产物 | S3 | 上传完成并登记后对用户可见 |
| 技能文件 | 继续使用 PostgreSQL | 复用 SkillFile；体积增长后另行评估 |
| 工具执行目录、临时文件、依赖缓存 | Worker 本地磁盘 | 按运行隔离，完成后按策略清理 |
| 历史归档 | 可选 S3 | 不承担在线事务查询 |

不将会话 JSONL 原样迁到 S3 后继续追加。对象存储按对象更新，不承担本地文件追加、数据库事务或多写者互斥职责。第一版将在线会话内容迁回 PostgreSQL。

S3 不直接挂载为 Agent 的普通文件系统。工具继续操作本地路径，由服务端下载输入、上传产物。

## 5. 文件模型与读写流程

### 5.1 存储抽象

增加 `ArtifactStore`，提供上传、下载、删除和生成短期下载链接等能力，支持 `local` 与 `s3` 两个实现。单机开发允许 local；集群模式启动时校验必须使用共享对象存储。

数据库新增文件元数据模型，建议包含：`id`、`userId`、`conversationId`、`runId`、`storageBackend`、`objectKey`、原始文件名、MIME 类型、字节数、内容哈希、状态、创建时间与删除时间。文件状态至少区分 uploading、ready、failed、deleted。历史文件必须记录后端，不能因修改全局配置而失去定位能力。

业务引用使用 `fileId`，对象 key 由服务端生成，不使用用户提供的路径；本地绝对路径只在对应 Worker 内有效。文件修改生成新对象和新版本，避免覆盖正在被其他运行读取的输入。

### 5.2 输入与产物

1. API 鉴权并创建上传记录，将文件写入对象存储；首期可由后端代理上传，后续再增加直传。
2. 校验大小和哈希，成功后将记录标记为 ready。未完成文件不能作为 Run 输入。
3. 创建 Run 时冻结输入文件版本和工作区版本。Worker 领取任务后，将输入下载到隔离目录并验证完整性。
4. Agent 在本地读写文件。通过受控输出目录或显式发布工具选择产物，不自动上传整个工作目录，避免将凭据、缓存和临时文件作为附件发布。
5. 上传产物到不可变对象 key，提交文件记录及运行结果；只有产物上传并登记成功，运行才可报告交付成功。
6. 上传失败进入有界重试或明确失败，保留已持久化的部分结果，不返回失效的本地路径。

对象存储和数据库之间没有跨系统事务。通过 uploading / ready 状态、幂等上传和后台对账解决中断：清理超期未引用对象，检测 ready 记录对应对象缺失，并记录可观测错误。删除先写墓碑，再异步删除对象；重试必须检查引用关系。

### 5.3 连续会话的文件恢复

需要跨轮保留的文件，使用版本化工作区清单保存逻辑路径、fileId 和哈希。下一轮 Worker 根据清单恢复文件，不依赖上轮执行节点。

同一会话同一时间只允许一个写入运行。清单通过 revision 条件更新；只有持有有效执行租约的 Worker 才能发布新版本。失败运行的文件先保留为该次运行的产物，不自动替换最近成功工作区。

首期持久化范围为上传输入和受控输出。若技能需要修改项目源码、Git 仓库或任意外部目录，必须显式定义独立的工作区存储与版本策略；在完成该适配前，这类任务绑定专用节点，不宣称可以任意接管。

### 5.4 访问与生命周期

桶保持私有。后端按用户和文件归属鉴权后代理下载或签发短期链接，禁止直接返回长期公开地址。签名链接视为临时凭据，不写入持久消息和日志。

配置上传大小、用户配额、临时对象过期时间和产物保留策略。下载落盘需校验路径，拒绝绝对路径、`..` 穿越及越界符号链接。S3 endpoint、region、bucket、认证信息通过环境变量注入，真实凭据不提交到 Git。

## 6. 运行领取、租约与故障恢复

Run 增加执行归属与控制字段，例如 `ownerId`、`leaseUntil`、`executionEpoch`、`heartbeatAt`、`cancelRequestedAt`、`attempt`。字段名称在实施时确定。

Worker 通过数据库事务原子领取 queued 任务；可使用行锁和 `SKIP LOCKED`。领取时更新租约和执行代次，执行期间周期性续租。所有状态、checkpoint、事件及工作区发布必须校验当前代次和租约；旧 Worker 失去租约后停止执行并被拒绝写入。

恢复服务只处理租约过期的运行，禁止启动时扫描并失败所有未完成运行。会话 activeRunId 的清理与 Run 终态在同一事务内完成，并检查仍指向该 Run。

租约只能约束内部提交，不能撤销已经发往外部服务的请求。任务默认按可能重复执行设计，外部副作用使用稳定幂等键。对不可幂等的发送、支付或外部修改，故障后标记 interrupted / 待确认，不自动重放。checkpoint 恢复不等于可以从任意工具调用中间安全续跑。

取消请求先持久化，再通知执行节点。Worker 定期检查取消状态，并通过本地 AbortController 中止；Redis 通知丢失时仍能通过轮询生效。

## 7. SSE 与事件一致性

持久事件以 `(runId, seq)` 唯一标识，按当前执行代次校验写入。API 按客户端游标查询历史，按序去重输出；实时通知用于唤醒补拉，不承载唯一事件副本。定期补拉覆盖通知遗漏及订阅切换窗口。

关键事件、消息投影、checkpoint 和终态必须具备可靠提交与恢复规则。允许合并 token 增量以控制写入量，但客户端已确认的持久游标不能越过尚未可靠保存的数据。需要重新设计当前允许丢弃事件的缓冲逻辑，并确定持久化吞吐与交互延迟预算。

任意 API 都能订阅同一个 Run；SSE 连接断开不取消后台执行。数据库不可用时不能伪装为正常完成，恢复后从最后持久游标继续。

## 8. 定时任务

第一版仅启动一个 Scheduler，其他角色禁止启动本地 cron 和全局执行恢复。Scheduler 只创建任务，不直接执行长任务；修改和禁用计划通过共享数据库被调度器读取。

周期触发以 `(taskId, scheduledAt)` 建立唯一约束，手动触发使用独立请求幂等键。明确补跑策略、时区、重试和重叠执行规则。已有一次性任务的条件领取逻辑可复用，但不能替代周期触发去重。

后续运行多个 Scheduler 时，通过数据库租约竞争调度权；唯一约束作为重复创建的最终保护。任务重试使用共享持久记录，不依赖进程内定时器。

## 9. 迁移与部署

1. 新增文件存储接口、对象存储适配器与配置校验，保留单机 local 模式。
2. 在单实例维护窗口暂停写入，备份本地会话目录和数据库，将 JSONL 消息、事件及 checkpoint 幂等导入 PostgreSQL。
3. 按会话校验数量、顺序、哈希、消息投影和 checkpoint 可恢复性；校验完成后切换存储标记，原文件只读保留。迁移失败的会话不得提前切换。
4. 将需要保留的本地附件和产物导入 S3，建立 fileId 映射；不存在或无法归属的本地路径显式记录为不可用，不静默转换。
5. 引入角色、租约、事件补拉和取消协议，先单 API + 单 Worker 验证，再增加第二个 API。
6. 最后增加多个 Worker 和 Scheduler 高可用，完成故障验收后再开放自动扩容。

Compose 去掉固定容器名与每副本宿主机端口，由网关统一暴露；数据库迁移作为独立部署步骤只执行一次。网关支持 SSE 长连接、禁用响应缓冲并配置心跳和超时。

Worker 停机时先停止领取，继续续租并等待已有任务结束；超过退出期限按故障恢复策略处理。数据库连接池和 Worker 并发按总副本数限制，避免扩容耗尽数据库或模型配额。

上线前保留旧版本和备份。切换后产生的新数据不能仅靠回滚二进制恢复到旧 JSONL 模式；回退需暂停写入并执行验证过的反向迁移，或使用兼容新存储的旧版本。

## 11. 验收标准

- 两个 API 并发发送同一个请求，只创建一个 Run；同一会话不同请求不会并发写入。
- 在 API A 创建、API B 订阅与取消，得到同一事件序列和终态；重连、通知丢失及通知重复均不产生永久缺口。
- 新实例启动不会修改其他节点仍持有效租约的运行或定时执行。
- Worker 宕机后只恢复过期租约；旧 Worker 恢复后无法写入状态、事件或工作区清单。
- 不可幂等工具中断后不会自动重放；可重试工具使用相同业务幂等键。
- 两个 Scheduler 同时触发同一计划时只生成一个调度任务，计划禁用和修改在规定轮询周期内生效。
- 在 Worker A 上传输入并生成产物，后续运行由 Worker B 正确恢复；API 任意节点均可下载。
- 上传、数据库登记、删除各阶段故障可重试，孤立对象可回收，ready 文件缺失能够告警。
- 跨用户文件访问、伪造对象 key、路径穿越和过期下载链接均被拒绝。
- 本地 JSONL 迁移前后消息数量、顺序、终态和 checkpoint 一致；抽样完成真实续聊与文件读取。
- 滚动发布、Redis 不可用、S3 暂时不可用、数据库中断均有明确用户状态，不返回虚假的交付成功。

实施时增加数据库并发与租约集成测试、对象存储契约测试、SSE 断线恢复测试和多进程故障测试。按仓库要求运行 `pnpm check`、`pnpm test`；吞吐、补拉延迟、取消延迟和恢复时限需在上线前按实际部署环境确定并验证。
