# 历史消息服务端存储与多设备同步需求

状态：已实施服务端存储、前端切换、多页面同步与版本化模型上下文检查点；验证记录见第 11 节。

## 1. 目标与范围

将聊天历史的权威数据源从浏览器 IndexedDB 迁移到服务端 PostgreSQL。同一账号连接同一服务端时，Web、桌面端及后续移动端可以查看、续聊并同步同一批会话。

首期包含：会话列表、消息分页、标题、Agent 归属、运行状态、实时消息同步、断线补拉、删除同步和账号隔离。保留当前首条用户消息作为默认标题、自动标题不覆盖手动标题、空草稿不进入历史等行为。

首期不包含：旧 IndexedDB 数据迁移、多人协作共享会话、离线发送队列、消息编辑与分支、不同服务端之间复制数据、附件文件跨端上传。已有消息中的工具结果、思考内容等按当前展示规则保留；本机文件路径不代表另一设备能访问文件。

多端共享前提是同一账号、同一后端及数据库。各设备各自启动独立的本地伴生服务，不会因此自动共享历史；local 模式仅提供对应服务实例内的历史，跨设备使用采用现有 Supabase 登录模式和统一后端。

## 3. 用户可见行为

1. 设备 A 发送后，设备 B 自动出现该会话；打开时可看见已有内容和正在生成的回复。
2. 任一设备重命名、自动生成标题或删除会话，其他在线设备同步更新。
3. 生成期间刷新、切换设备或关闭页面，服务端继续运行；重新打开后恢复已保存内容，并订阅当前运行。显式点击停止才取消运行，需调整当前客户端连接与取消行为。
4. 网络中断显示“连接中断，正在重连”；发送未获确认时显示待确认状态，通过同一请求标识重试，不重复执行。
5. 另一设备已在该会话生成时，禁止并发发送，提示“该会话正在回复中”；仍可查看和停止。
6. 初次加载、空列表、加载失败分别展示；服务不可用不能伪装成“暂无历史”。
7. 切换账号立即清空旧账号的内存状态、关闭订阅；迟到响应不能写入新账号页面。

建议同步指标：正常网络下，新消息与元数据变更提交后 2 秒内在其他在线设备可见；重连后完成补拉，无永久缺漏或重复。

## 4. 存储与写入原则

服务端负责新增消息和更新回复，客户端不再周期性上传整个消息数组。Run / RunEvent 保留执行审计用途，会话消息表作为展示查询模型，避免列表加载时回放全部事件。

建议数据模型：

| 模型 | 关键字段与约束 |
| --- | --- |
| Conversation | id、userId、agentId、executionConfig（版本化且不含凭据）、title、titleSource（fallback/generated/manual）、createdAt、updatedAt、lastMessageAt、revision、deletedAt |
| ConversationMessage | id、conversationId、seq、runId、role、content（版本化 JSON）、status、appliedEventId、createdAt、updatedAt；唯一 conversationId + seq |
| ConversationChange | 按用户提交顺序递增 changeId、userId、conversationId、revision、type、createdAt；保存变更通知与删除墓碑；唯一 userId + changeId |
| ConversationSyncState | userId（唯一）、lastChangeId；事务内锁定并分配该用户的变更游标 |
| Run 扩展 | clientRequestId；按 userId + clientRequestId 唯一，重复请求返回原 run |

具体字段名在实施时对齐现有类型；消息 JSON 使用服务端定义的稳定 DTO 和 schemaVersion，经适配层转为 assistant-ui 类型，不让数据库直接依赖 UI 库类型。工具调用 ID、结果、错误、思考内容及内容块顺序需要完整表达。

- 新发送在同一事务中确认会话归属、创建用户消息与 Run、记录变更；事务成功后才能开始执行。
- 同一请求重试若 payload 不同返回冲突；同一 payload 返回原结果，不重复追加用户消息。
- 回复使用稳定 messageId，增量事件按现有 Run seq 排序与去重；持久化必须先于对外确认。消息投影可批量更新，但必须能从持久事件重建未完成投影。
- 每次回复投影将内容与 `appliedEventId` 在同一事务更新，表示该 run 已连续应用到的事件 ID；不能用最新持久事件 ID 代替投影水位。一个 run 的回复内容作为整体投影和替换，终态也须推进水位。
- 终态与完整回复投影一致提交后，才发布完成通知。持久化失败不向客户端宣告保存成功。
- conversation revision 是服务端版本，不能依赖客户端时间做冲突判断；lastMessageAt 用于历史排序，标题修改不改变消息时间。
- 标题生成在服务端执行并条件更新，仅当来源仍非 manual 时写入；客户端断开不影响标题落库。
- 新表沿用现有后端数据库权限及 RLS 策略，添加 userId 和排序查询索引；浏览器不直接操作数据库。

## 5. 接口与同步协议

接口路径为建议设计，保留现有 Run SSE 通道。

| 接口 | 行为 |
| --- | --- |
| GET /api/conversations | 按 lastMessageAt、id 游标分页，仅返回摘要；支持 agentId 筛选 |
| GET /api/conversations/:id | 元数据、revision、activeRunId、executionConfig 和上下文可用状态；消息事件水位随消息接口返回 |
| GET /api/conversations/:id/messages | 按 seq 分页，支持 beforeSeq 加载更早消息及 afterSeq 补拉；同一数据库快照返回内容、revision 及每个回复的 runId + appliedEventId |
| PATCH /api/conversations/:id | 携带 expectedRevision 修改标题；冲突返回 409 和最新版本 |
| DELETE /api/conversations/:id | 幂等软删除，生成墓碑与变更记录 |
| GET /api/conversations/changes | 当前用户的 SSE 变更流，支持 afterChangeId 续传 |
| POST /api/runs | 增加 clientRequestId、expectedRevision，返回 runId、稳定消息 ID 和当前 revision |

消息 seq 只解决新增消息顺序，已存在的流式回复更新通过 Run SSE 和会话 revision 识别，不能仅用 afterSeq 判断已完全同步。

首次建立同步时，列表首屏与当前用户的 `lastChangeId` 在同一数据库一致性快照内读取并返回，客户端从该水位订阅变更，避免“先查列表、后订阅”期间漏事件。后续列表页按 ID 合并，并以 revision 拒绝旧数据；已收到的删除墓碑优先于旧页面响应。收到变更后按需重新查询权威数据。

消息快照与 Run SSE 使用独立于用户级 changeId 的事件水位。打开运行中会话时，先取得含 `runId + appliedEventId` 的回复快照，再以该 `appliedEventId` 作为 `afterEventId` 补拉。客户端维护每个 run 已连续应用的事件 ID，忽略重复事件；新快照水位低于本地水位时拒绝覆盖，相等时内容应一致，更高时整体替换该 run 的回复并从新水位继续。初次订阅前若已有事件进入本地缓冲，仅应用高于快照水位的部分。不能将仅在详情接口读取的水位与另一次请求的消息内容拼接使用，也不能从最新持久事件 ID 跳过投影尚未包含的事件。

Run SSE 保留现有路径，但必须修复 `streamRun` 的回放与订阅竞态：完成鉴权后先注册监听并缓冲实时事件，再读取持久历史；按事件 ID 有序合并历史与缓冲、去重后切换到实时发送，切换期间的新事件仍进入同一队列。监听与回放建立后重新读取 Run 状态，确保补拉期间结束的运行也能发送终态并关闭连接；终态已被游标覆盖时直接结束。断开连接须在所有分支释放监听。用户级变更 SSE 同样使用无遗漏的补拉与监听衔接，并以持久变更周期补查兜底。

变更通知与业务更新同事务落库，通过提交后的通知与周期补查发送；不能只依赖进程内广播。`changeId` 是用户内游标，不能直接采用 PostgreSQL sequence / 自增 ID 作为提交顺序。每个变更事务先创建（不存在时）并锁定该用户的 `ConversationSyncState` 行，再执行会话业务更新、递增 `lastChangeId` 并写入变更记录，锁持有到提交或回滚；所有变更入口遵循相同锁顺序。同一用户的其他变更事务必须等待，因此不会出现 11 已提交并被消费、10 随后才提交的遗漏。回滚同时撤销计数与变更，SSE 只能按已提交的 changeId 推进游标。保留窗口建议 30 天，游标过期返回明确的 reset_required，客户端重新拉取快照。运行结束后仍保持用户级变更订阅。断线使用退避重连，页面回到前台主动校验；同步延迟指标按在线状态衡量。

所有查询、订阅、取消与写入均从服务端认证信息取得 userId，不接受客户端指定所有者。访问其他用户资源返回 404。静态 changes 路由需避免被 :id 路由误匹配。

首期保持单后端实例部署约束，复用现有会话运行锁；若后续多实例部署，需要数据库级运行占用锁、跨实例事件通知，并替换当前全局 interrupted 恢复逻辑，不能只扩容进程。

## 6. 删除与并发处理

- 删除和运行创建必须串行校验同一会话，避免删除期间新建 Run。
- 删除运行中的会话：先记录墓碑并请求取消；迟到事件不得重新创建会话或使其出现在列表。
- 两设备同时发送时，只接受一个符合 revision 且未被占用的请求；另一请求返回明确冲突，刷新后由用户决定再次发送。
- 标题冲突不静默覆盖，自动标题不能覆盖人工命名。
- 墓碑保留覆盖同步游标有效期；游标过期需重新拉取快照。Run 审计清理策略另定。

## 7. 切换策略

直接切换到服务端存储，不读取、上传或合并旧 IndexedDB 历史，不提供迁移提示和导入接口。服务端无历史时展示空列表。移除历史消息的 IndexedDB 读写，不继续双写；旧数据库不自动清理。

## 8. 续聊上下文边界

跨设备续聊必须绑定同一会话执行配置，连接同一服务端本身不足以保证复用内存上下文。首次发送时服务端解析并固定版本化 `executionConfig`，包含模型协议、规范化 Base URL、模型 ID、凭据来源（server/client，不含凭据值）、解析后的服务端工作目录及 Agent/技能上下文指纹；配置不含 API Key。后续设备从会话读取此配置，不能将本机默认模型或目录自动用于已有会话；显式提交不同配置返回 `409 conversation_execution_config_mismatch`，提示使用原配置或新建会话。

首期不新增凭据同步或持久凭据库：使用服务端环境凭据的会话由服务端继续解析；使用客户端自带凭据的会话要求续聊设备提供与绑定端点匹配的凭据，缺失时返回明确的 `credential_required`，不回退到另一模型配置。凭据仅用于本轮认证，不能下发给其他设备或写入会话、检查点、幂等 payload 原文及日志。有效凭据更换不应重置模型记忆：运行时上下文改为按用户、会话与执行配置版本归属，适配器的凭据缓存键不能决定上下文是否存在；沿用会话锁，在每轮执行时绑定凭据并复用该上下文。此调整属于首期运行链路改造。

详情接口返回 `contextState`（available / not_restored / unavailable）及可操作原因；内存上下文不存在时明确提示，不能静默创建空上下文后宣称正常续聊。后端重启后，仅恢复展示历史不足以实现有记忆的续聊。

建议将模型上下文持久化与恢复纳入完整验收：保存按用户、会话及模型配置隔离的版本化上下文检查点，包括工具调用/结果配对和 compact 后的摘要；在同一会话锁内恢复并继续执行。禁止将界面展示的脱敏消息直接当作完整模型上下文。检查点存储需遵守现有秘密保护策略，不保存 API Key；无法安全持久化的内容需要明确恢复降级行为。

若分期交付，第一阶段可先支持历史同步，但重启后必须明确提示上下文未恢复，不能无提示地声称支持完整续聊；第二阶段完成检查点后再通过重启续聊验收。工作目录仍是服务端路径，切换设备不能将另一设备的本机路径直接用于执行；沿用现有 Agent 与技能上下文变更校验。

## 9. 实施拆分与交付顺序

1. **服务端数据层**：Prisma 表和迁移、消息 DTO、会话仓储、用户隔离、分页、revision、投影事件水位、按用户提交有序的变更游标与删除墓碑。
2. **运行链路接入**：发送幂等、用户消息事务写入、事件投影、执行配置绑定及凭据与会话上下文解耦、失败/取消/重启恢复、服务端标题；确保浏览器断开后仍保存输出。
3. **前端切换**：conversation-store 改用 API；列表和消息分页；移除 250ms 整段持久化及卸载即取消；显示加载、错误、冲突和运行状态。
4. **多端同步**：用户级变更流、一致性快照及事件水位、Run SSE 回放/订阅竞态修复、续传、去重、重连和账号切换防护。
5. **上线切换**：直接启用服务端历史，移除旧 IndexedDB 历史读写，小范围验证后发布。
6. **上下文恢复**：模型检查点、压缩后恢复与跨重启续聊，完成最终能力验收。

回滚保留新增表与已经写入的历史，避免回滚时删除数据。前端回退版本不具备读取服务端新历史的能力，因此应优先修复或回退服务端实现且维持新 API 契约；不能将旧 IndexedDB 当成服务端历史的完整备份。

## 10. 验收与验证

- 两个独立浏览器会话登录同账号：发送、流式输出、标题、取消和删除均同步，消息顺序一致且不重复。
- 同账号设备配置不同：B 的本机默认模型、端点或目录不覆盖 A 的会话配置；按会话配置且凭据可用时能引用 A 的事实，显式配置不匹配返回冲突，缺凭据时明确阻止发送。更换有效凭据不丢失上下文，其他设备与接口响应无法读取 A 的凭据。
- 回复投影落后持久事件时，以投影水位打开会话并补拉，内容既不重复也不遗漏；低水位快照迟到不能覆盖较新的本地回复，高水位快照整体替换后可继续正确消费增量。
- 注入同一用户两笔并发变更，阻塞第一笔提交，验证第二笔不能越过其游标被消费；回滚后仍能正确续传。列表快照与变更提交交错时无永久遗漏。
- 在 Run SSE 回放、缓冲排空和切换实时发送期间分别注入增量及终态，验证顺序、去重、终态关闭及监听释放；游标已覆盖终态时连接正常结束。
- 不同账号：列表、详情、SSE 与 Run 操作均无法访问对方数据；账号切换无旧内容闪现。
- 关闭发起设备、刷新、网络断开重连后，回复继续保存；接收设备恢复到同一终态。
- 重复发送请求不重复执行；两设备并发发送、旧 revision 改名、删除与迟到事件得到确定结果。
- 重启期间运行标为 interrupted，已保存部分回复可见；完成上下文阶段后，后续问题能引用重启前事实与 compact 摘要。
- 万条会话列表和长消息历史采用分页，列表响应不包含整段正文。
- 本机已有 IndexedDB 历史时，新版仅展示服务端数据，不读取或上传旧记录；服务端为空时正确展示空列表。
- 数据库提交失败时不返回保存成功；事件已提交而投影中断时可以恢复一致状态。

实施时增加后端路由/仓储/运行恢复测试，以及前端加载、重连、账号切换和运行同步交互测试。按仓库要求运行 `pnpm check` 和 `pnpm test`，再用两个真实客户端完成同步验收。

- 用户变更流每 750ms 查询持久记录，不依赖进程广播；同页面列表与当前会话共享连接。前端收到变更后读取权威消息快照，按 revision 拒绝旧快照，因此不在客户端拼接 Run 增量。Run SSE 仍支持按事件水位补拉，已修复回放与订阅竞态、终态关闭和断开清理。
- 前端停止使用 IndexedDB，会话和消息均按页读取；空草稿不落库。发送请求使用稳定请求 ID，未确认时以相同内容重试；关闭或切换页面不发送取消，只有停止操作调用取消 API。账号切换清空 revision 缓存并中止所有订阅。
- 会话绑定无凭据执行配置，其他设备读取绑定模型与服务端目录。不同执行配置、缺失凭据、revision 冲突均返回明确错误；标题由服务端独立生成，不覆盖人工标题，也不占用下一轮执行锁。
- 按会话保存完整模型消息检查点，包含工具消息与压缩摘要；从检查点恢复模型消息，换用有效凭据仍沿用该上下文。检查点经过秘密保护检查，若包含不能安全持久化的内容，保存明确的 `unavailable` 标记，重启后阻止静默空上下文续聊。检查点从不经会话详情或列表返回。
